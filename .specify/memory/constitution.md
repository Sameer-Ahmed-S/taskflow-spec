# TaskFlow Constitution

## Core Principles

### I. Spec-First (NON-NEGOTIABLE)
Every feature starts in `taskflow-spec`. No code is written in any implementation
repo until the feature's spec PR is merged. Requirements, contracts, and plans live
in the spec repo; implementation repos receive read-only synced copies.

### II. Contract-First
API shape is defined in `contracts/tasks-api.yaml` (OpenAPI) before implementation.
Backend implements exactly the contract; frontend consumes exactly the contract.
Contract changes require a spec update first.

### III. Multi-Repo Change Order (ADR-002)
Cross-repo changes land in this order, one PR per repo:
1. taskflow-spec (spec + contract)
2. taskflow-db (migration)
3. taskflow-backend (contract implementation)
4. taskflow-frontend (contract consumption)

### IV. Traceability
Every implementation PR references the spec feature directory and commit it
implements (e.g. "Implements specs/001-task-priority @ <sha>"). Tasks in
`tasks.md` are tagged per repo ([db], [backend], [frontend]) and checked off in
the spec repo when their PR merges.

### V. Server-Side Authority (ADR-003/005)
IDs and timestamps are generated by the backend, never sent by clients. The
datastore is embedded SQLite; the backend applies migrations from `taskflow-db`
at startup.

## Governance
This constitution supersedes ad-hoc practice. Amendments require a PR on
taskflow-spec updating both this file and `decisions.md`.
